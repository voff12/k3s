# 自动化发布与 AI 监控产品形态设计

> 设计阶段：产品概念 / 评审稿（不含实现方案）
> 目标：把现有 K3s 管理平台从“集群资源管理 + 手动触发发布”提升为“以应用和发布为中心的交付运营台”。

## 1. 产品定位

### 1.1 用户要完成的事

- **开发者**：知道提交是否能发布；在一个地方看 PR 检查、预览环境和失败原因。
- **测试/产品**：找到本次变更对应的 Beta 版本，完成验证并留下结论。
- **发布负责人/运维**：了解正在灰度什么、是否安全、发生异常时如何恢复。
- **管理者**：了解版本交付效率、线上质量、未处置风险和自动化覆盖度。

### 1.2 产品承诺

首页首先回答四个问题：

1. **现在什么需要我处理？**（发布审批、失败检查、告警、待验收）
2. **最近哪些应用发生了变化？**（PR、构建、部署、灰度、回滚）
3. **线上是否健康？**（服务 SLO、异常趋势、受影响范围）
4. **我怎么追到证据？**（提交、镜像、部署、指标、日志、AI 结论的完整链路）

界面从集群对象列表导向“应用交付旅程”。Pod、Node、存储和终端能力保留，作为运维工作区的能力，不再占据发布主流程的首页中心位置。

## 2. 信息架构

建议一级导航：

| 一级导航 | 子页面 | 核心用户问题 |
|---|---|---|
| **交付总览** | 全局概览、待处理、最近活动 | 当前交付和线上状态如何？ |
| **应用** | 应用目录、应用详情、环境配置 | 每个服务如何构建、部署和观察？ |
| **发布** | 发布列表、发布详情、预览环境 | 版本走到哪一步，门禁依据是什么？ |
| **运行质量** | 服务 SLO、告警事件、AI 分析 | 线上异常是什么、影响谁、该怎么处理？ |
| **集群运维** | 集群概览、工作负载、Pod、内存、存储、终端 | K3s 资源是否健康，具体对象出了什么问题？ |
| **平台设置** | 仓库连接、镜像仓库、通知、权限、策略模板 | 平台如何连接团队现有系统并管理规则？ |

将当前 DevOps、Release 和多分支预览能力统一到“发布”；将 AI 问答从独立的泛聊天入口调整为“上下文式分析”，仍保留通用问答入口但不作为主导航的第一目标。资源运维模块继续存在，放入“集群运维”下。

## 3. 核心对象模型（用户视角）

用户不应分别理解 PipelineRun、ReleaseRecord、Deployment、Pod 等底层对象。产品统一呈现以下业务对象：

- **应用**：代码仓库、运行时、负责人、服务等级、默认环境、监控入口。
- **变更**：PR/提交、关联需求、变更摘要、检查结果。
- **构建制品**：不可变镜像摘要、构建来源、扫描/SBOM 状态。
- **发布**：一次变更从 Preview 到 Beta/生产的完整记录。
- **环境部署**：某个应用在某个环境实际运行的制品及状态。
- **事件**：发布异常、SLO 告警、AI 分析和人工处置。

首页、应用详情、发布详情和事件详情始终用应用名、环境名、版本/digest 和时间线互相关联。

## 4. 关键页面设计

### 4.1 交付总览

顶部只放高价值摘要：

```text
交付总览      集群：生产 K3s ▾       24h ▾

待处理  3        正在发布  2        线上异常  1        今日成功发布  8

需要我处理                       正在进行
支付服务 · Beta 验收待确认       订单服务 · Canary 20% · 观察中
用户服务 · 安全扫描失败          搜索服务 · Beta 测试中

服务健康趋势  [成功率 / 延迟 / 流量选择器]

最近活动
10:42 订单服务 v2.8.1 进入 20% 灰度
10:21 支付服务 PR-482 Preview 验收通过
09:58 用户服务构建因 Critical 漏洞被阻断
```

交互原则：

- 默认按“需要处理”排序，不把 Pod 数量和 CPU 饼图当首页主内容。
- 每张待处理卡片明确对象、环境、原因、阻断项和下一步入口。
- 指标卡片都可下钻到服务或事件；过滤器跨页面保留所选集群/环境。
- AI 总结只作为带证据链接的辅助摘要显示，不替代告警状态或业务指标。

### 4.2 应用目录与应用详情

**应用目录**是发布与运行质量的入口，列表列出：应用名、负责人、当前生产版本、Beta/灰度状态、SLO 状态、最近发布时间、待处理事项。

应用详情采用固定标签页：

1. **概览**：代码仓库、负责人、运行时、生产/Beta 版本、服务健康和待处理风险。
2. **发布**：此应用的版本时间线、当前灰度、历史回退。
3. **环境**：各环境的版本、配置差异、部署健康、预览环境。
4. **质量**：服务 SLO、错误率/延迟/业务指标、告警和 Trace/日志入口。
5. **设置**：构建规则、健康检查、发布策略、通知和权限。

新建应用优先采取“连接仓库 → 自动识别运行时/容器定义 → 选择集群和命名空间 → 预览配置 → 完成”的向导。自动识别结果需要用户确认；不在首屏一次性暴露所有 Maven、Python、Harbor、K8s 参数。

### 4.3 发布详情（最重要页面）

发布详情用一条横向/纵向阶段时间线统领数据：

```text
PR 检查 ─ 构建制品 ─ Preview 验证 ─ Beta 验收 ─ 生产灰度 ─ 稳定发布
 通过       通过         通过         待确认       20% 观察中       未开始
```

页面布局建议：

- **顶栏**：应用名、环境、版本、状态、提交 SHA、制品 digest；操作按钮按角色和状态展示。
- **阶段进度**：完成/运行中/阻塞/跳过，每阶段显示开始时间、耗时、结论和详情链接。
- **变更摘要**：PR/需求、提交列表、变更文件、自动生成的变更说明。
- **质量证据**：单测、契约/e2e、扫描、SBOM、签名/来源证明。
- **发布健康**：灰度流量比例、stable/canary 两组指标对比、样本数和观察窗口。
- **AI 分析**：摘要、严重度、置信度、证据引用、待人工确认项。与规则门禁分区展示。
- **操作记录**：谁批准、暂停、继续、回滚，何时操作、使用了哪个策略。
- **关联日志**：可搜索的构建日志、Kubernetes Event、服务日志和 Trace。

按钮随发布状态变化：

| 状态 | 主操作 | 次操作 |
|---|---|---|
| 检查失败 | 查看失败项 | 重新运行可重试步骤 |
| Beta 待验收 | 通过验收 / 退回修复 | 查看测试证据 |
| 灰度观察中 | 暂停扩流 | 查看指标；回退需二次确认并要求原因 |
| 策略判定暂停 | 查看触发规则 | 重试评估 / 人工豁免（有权限、填写理由） |
| 稳定运行 | 查看报告 | 发起下一版本 |

破坏性操作需要在确认框中重述应用、环境、版本、影响范围和依据。例如回滚确认写明“将生产流量切回 v2.8.0，当前 20% 新版本流量停止”，不能仅出现“确定吗？”。

### 4.4 预览环境

预览环境以 PR 为主线，而非给用户一个需要手动清理的临时 namespace：

- PR 标题、分支、合并基线、预览 URL、部署状态和过期时间。
- 冒烟/e2e 执行结果与失败定位。
- “续期”“重新部署”“打开应用”“删除预览”按权限出现。
- 自动回收时间可见；删除支持确认并展示将释放的资源。
- 多分支联调预览明确列出 base 与被合并分支、冲突状态及最终 commit SHA。

### 4.5 运行质量与 AI 事件详情

**事件列表**按影响而非日志数量排序，字段包括：严重度、受影响应用/环境、开始时间、是否与近期发布相关、当前负责人、处置状态。

事件详情采用证据链：

```text
发生了什么 → 影响范围 → 触发指标/告警规则 → 相关发布/变更
            → 代表性日志/Trace → AI 根因候选与置信度
            → 建议步骤 → 人工处置/验证结果
```

AI 卡片必须标清：哪些是观测事实、哪些是模型推断、哪些证据支持推断、置信度如何。可提供“复制排查摘要”“生成工单描述”“标注此分析有帮助/不准确”等操作；在本产品阶段不提供“让 AI 自动修复”按钮。

### 4.6 集群运维

当前节点、Pod、终端、内存、存储和 K8s 事件能力收拢到此空间。保留专业排障效率，同时让日常发布用户不必先理解 K8s 对象。资源页面增加“关联应用/发布”跳转；从发布详情可以直接跳到对应 Pod、事件、日志和终端。

## 5. 发布体验状态与文案

使用清晰的业务状态，不以模糊的“运行中/失败”覆盖所有阶段：

`排队中 → 代码检查 → 构建中 → Preview 验证 → Beta 待验收 → 灰度观察中 → 稳定发布`

分支状态包含：`阻塞`、`暂停待处理`、`回退完成`、`已取消`、`验收失败`。每个状态配一个原因、证据和下一步，不只用颜色区分；页面和通知中同时提供文本状态。

门禁结果分成三种：

- **通过**：数据满足策略。
- **失败**：明确违反阈值/规则，说明阻断原因。
- **证据不足**：样本不足、观测未接入或窗口未完成。不得显示成绿色通过。

## 6. 通知产品形态

通知采用“有动作才推送”：

- PR 阻断：推送失败检查摘要和修复入口。
- Beta 验收：推送测试摘要与验收链接。
- 生产暂停/回退：立即推送应用、环境、影响、硬规则触发原因和当前状态。
- AI 新分析：附摘要与证据链接；相同事件归并更新，避免重复刷屏。
- 稳定发布：推送发布报告链接和本次版本摘要。

通知渠道由团队设置页维护；高危发布事件需支持去重、升级与静默时段策略，审计记录始终保留。

## 7. 权限与自动化的产品表达

产品不应该把自动化描述成“全自动等于没有人”。按风险和角色展示自动动作边界：

| 动作 | 默认产品行为 |
|---|---|
| 构建、扫描、Preview 部署 | 条件满足后自动执行 |
| Beta 部署 | PR 合并后自动执行；验收由测试/产品确认（可按团队策略调整） |
| 生产灰度 | 低风险服务可自动开启；高风险服务支持发布负责人批准 |
| 灰度扩流 | SLO 规则通过自动推进；证据不足时暂停 |
| 紧急回退 | 明确硬规则触发后可自动执行，并立即通知；操作可追溯 |
| AI 建议 | 提供证据和建议；不能单独触发生产变更 |
| 人工豁免 | 限定角色，要求原因、范围、有效期，并记录审计 |

团队可以在应用设置中选择策略模板（低风险/标准/高风险），初始默认保守。只有经过一段时间影子运行后，管理员才可调整生产自动化级别。

## 8. 视觉与交互方向

- 面向交付场景优先使用清晰的状态、时间线、指标趋势和证据链接；减少大屏式装饰图表。
- 信息密度允许专业用户快速扫读，但重要结论使用短句和直接操作入口。
- 状态颜色固定且全站统一：绿=通过/健康，黄=等待/观察，红=阻断/异常，灰=未运行/已取消；同时用标签和图标传达含义。
- 时间、环境和版本标识始终可见；所有指标展示时间窗口、单位、样本量和数据新鲜度。
- 首次接入使用空状态引导（连接仓库、注册应用、选择集群、定义健康检查），不要显示没有上下文的空图表。
- AI 设计避免聊天框吞没证据；主视图先呈现结论/事实/证据，聊天作为深入追问的补充。

## 9. 首期产品范围

### 首期要让用户体验到

1. 在首页看清待处理发布、正在灰度和服务异常。
2. 从一个应用详情进入某个版本，追踪它从 PR 到生产的全过程。
3. 看到所有门禁的“通过/失败/证据不足”和明确证据。
4. 在事件详情中看到规则结论与 AI 推断的区分，以及告警关联的发布。
5. 安全地执行暂停、回退、验收和人工豁免。
6. 从运维资源页在应用、Pod、发布和事件之间跳转。

### 暂不作为首期目标

- 自研完整 CI 引擎，或取代 GitLab/GitHub 的代码审查体验。
- 多集群多租户商业化计费控制台。
- 让大模型直接执行 kubectl、改配置或修复生产服务。
- 首期就同时兼容所有日志、监控、Git 和入口产品。
- 用 AI 分数取代确定性门禁或人工的高风险审批。

## 10. 产品评审需要确认的决策

1. 主导航是否以“交付总览 / 应用 / 发布 / 运行质量 / 集群运维”作为目标结构？
2. Beta 的默认验收人是测试/产品、研发负责人，还是完全策略自动验收？
3. 哪些应用可自动开启生产灰度，哪些必须人工批准？
4. 预览环境是本产品主打能力之一，还是仅作为发布详情中的辅助工具？
5. 告警通知首期优先接入钉钉、企业微信还是其他团队现有工具？
6. 首页首先服务运维值班，还是研发交付团队？这会决定默认集群视角与应用视角的比例。
